# Architectural decisions

One line per decision, newest at the bottom. Format: `YYYY-MM-DD — decision — why`.

- 2026-10-18 — Node.js installed via nvm (v24 LTS) rather than a system installer — user-scoped, no admin password, easy to upgrade/remove.
- 2026-10-18 — Next.js 16 with `cacheComponents: false` — the app is fully dynamic and auth-gated; Cache Components would force Suspense boundaries around every session read for no benefit.
- 2026-10-18 — `src/proxy.ts` (Next 16's rename of middleware) only refreshes the Supabase session and redirects anonymous users; role checks live in pages via `lib/auth/current-user.ts` so stale cookies can never grant section access.
- 2026-10-18 — OAuth starts server-side (`POST /auth/signin`) with `@supabase/ssr`, so no Supabase client runs in the browser; the anon key is still public-safe but simply unused there.
- 2026-10-18 — Allowed-domain check happens in `/auth/callback`; rejected users are signed out and their `auth.users` row deleted so no stray accounts accumulate.
- 2026-10-18 — First sign-in from an allowed domain auto-creates an `app_users` row with role `viewer` (sees nav + home only); `ADMIN_EMAIL` is forced to `admin` on every login. Role changes are done by editing `app_users` (no admin UI in phase 1).
- 2026-10-18 — `@supabase/ssr` and shadcn's own transitive deps (`@base-ui/react`, `cn`, `class-variance-authority`, `lucide-react`, `tw-animate-css`) are treated as part of the named stack; nothing else was added (no tsx/dotenv/zod/date-fns).
- 2026-10-18 — Scripts run with plain Node 24 (`node --env-file=.env.local scripts/x.ts`, native TypeScript stripping) instead of adding `tsx`/`dotenv`; `lib/appfolio/client.ts` therefore has zero framework imports.
- 2026-10-18 — Raw report tables (`raw_<report>`) are created on demand by the `ensure_raw_table`/`replace_raw_rows` SQL functions (service-role only), so adding a report never needs a migration; replacement is atomic (delete+insert in one function call).
- 2026-10-18 — Clean sales tables use text `id` primary keys (AppFolio id when present, else a composite key) and full-replace semantics: upsert everything seen this run, then delete rows with an older `synced_at`.
- 2026-10-18 — RLS is on for every table: authenticated users read only what their `app_users.role` allows (`current_app_role()` helper); all writes go through the service role in server code.
- 2026-10-18 — Cron route accepts both `Authorization: Bearer <CRON_SECRET>` (what Vercel Cron sends) and `x-cron-secret` (for external pingers like cron-job.org); Vercel Hobby only allows daily crons, so a 15-min schedule needs Vercel Pro or an external pinger.
- 2026-10-18 — Leasing season helper (`lib/season.ts`): leasing window Nov 1–Jul 31 per spec, but leads from Aug 1 onward count toward the *next* August's season so early fall leads aren't lost; Aug = "move-in", Sep–Oct = "pre-season". Confirm with the team.
- 2026-10-18 — AppFolio pagination follows `next_page_url` with the same POST body and `paginate_results: true`; if discovery shows the API expects GET for subsequent pages, change only `fetchReport` in `client.ts`.
- 2026-10-18 — Season definition finalized per owner: Nov 1 – Jul 31 for an Aug move-in; "current season" = the one we're in or the next one starting (Aug–Oct shows the upcoming season with zero counts until Nov 1). Supersedes the earlier "count from Aug 1" idea.
- 2026-10-18 — Seven confirmed reports (`property_directory, unit_directory, unit_vacancy, rent_roll, guest_cards, showings, rental_applications`) run sequentially with a 1.5s pause; `tenant_directory` exists but is not synced in phase 1.
- 2026-10-18 — `guest_cards` and `rental_applications` contain sensitive applicant data (income, credit score, addresses, employer, salary…): the mappers keep only an explicit allowlist and NO `raw_` jsonb copy is stored for these two reports. Note `showings` raw rows still include lead email/phone; flag if that should also be allowlisted.
- 2026-10-18 — The AppFolio database holds non-SCSH properties (51 properties / 376 units vs ~119 SCSH units), so a `properties` table carries our own `is_managed` flag: first sync marks everything managed, later-appearing properties default to unmanaged until an admin reviews them in `/admin/properties`. The Sales UI reads only through SQL views (`managed_*`, `available_units`) that join to `properties` and filter `is_managed = true`, so the filter cannot be forgotten in app code. Rows with no `property_id` are therefore excluded.
- 2026-10-18 — `units` is a composite of three reports merged in the sync (`unit_directory` base, `unit_vacancy` by `unit_id`, `rent_roll` by `unit_id` choosing one occupancy row: Current > Notice > Vacant > other > Future, latest move-in breaks ties). "Available" is defined once, in the `available_units` view: in `unit_vacancy` OR rent-roll status ≠ Current.
- 2026-10-18 — Reports that accept a date range are sent `from_date` = Aug 1 of the previous calendar year and `to_date` = today; if AppFolio rejects those params (400/422) the sync retries once without them and flags `dateParamsAccepted=false` in the result so the param names can be corrected.
- 2026-10-18 — Sales screens are URL-driven (tabs, filters, sorting are query params rendered on the server) and the whole season dataset is loaded in one request and filtered in memory — the data is small (~119 units, one season of leads) and this keeps the pages simple, bookmarkable and free of client state.
- 2026-10-18 — "Sync now" on `/admin` is a server action that calls `syncSales()` directly (same code path as the cron route) instead of HTTP-calling the route, so no secret has to be passed around; `maxDuration = 120` on that page.
- 2026-10-18 — Bug: first sign-in produced no `app_users` row because `SUPABASE_SERVICE_ROLE_KEY` held the publishable key (RLS blocked the insert) and the callback never checked supabase-js's returned `error`. Fix: `createSupabaseAdminClient` now refuses publishable/anon keys with an explicit message; provisioning moved to `lib/auth/provision.ts` which checks every error; `getCurrentUser` self-heals the row on any page load for allowed emails; failures are logged with `[auth]` prefixes and shown on the header role badge.
