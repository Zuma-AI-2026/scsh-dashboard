# Architectural decisions

One line per decision, newest at the bottom. Format: `YYYY-MM-DD — decision — why`.

- 2026-10-18 — Node.js installed via nvm (v24 LTS) rather than a system installer — user-scoped, no admin password, easy to upgrade/remove.
- 2026-10-18 — Next.js 16 with `cacheComponents: false` — the app is fully dynamic and auth-gated; Cache Components would force Suspense boundaries around every session read for no benefit.
- 2026-10-18 — `src/proxy.ts` (Next 16's rename of middleware) only refreshes the Supabase session and redirects anonymous users; role checks live in pages via `lib/auth/current-user.ts` so stale cookies can never grant section access.
- 2026-10-18 — OAuth starts server-side (`POST /auth/signin`) with `@supabase/ssr`, so no Supabase client runs in the browser; the anon key is still public-safe but simply unused there.
- 2026-10-18 — Allowed-domain check happens in `/auth/callback`; rejected users are signed out and their `auth.users` row deleted so no stray accounts accumulate.
- 2026-10-18 — First sign-in from an allowed domain auto-creates an `app_users` row with role `viewer` (sees nav + home only); `ADMIN_EMAIL` is forced to `admin` on every login. Role changes are done by editing `app_users` (no admin UI in phase 1).
- 2026-10-18 — `@supabase/ssr` and shadcn's own transitive deps (`@base-ui/react`, `cn`, `class-variance-authority`, `lucide-react`, `tw-animate-css`) are treated as part of the named stack; nothing else was added (no tsx/dotenv/zod/date-fns).
- 2026-10-18 — Scripts run with plain Node 24 (`node --env-file=.env.local scripts/x.ts`, native TypeScript stripping) instead of adding `tsx`/`dotenv`; `lib/appfolio/client.ts` therefore has zero framework imports.
- 2026-10-18 — Raw report tables (`raw_<report>`) are created on demand by the `ensure_raw_table`/`replace_raw_rows` SQL functions (service-role only), so adding a report never needs a migration; replacement is atomic (delete+insert in one function call).
- 2026-10-18 — Clean sales tables use text `id` primary keys (AppFolio id when present, else a composite key) and full-replace semantics: upsert everything seen this run, then delete rows with an older `synced_at`.
- 2026-10-18 — RLS is on for every table: authenticated users read only what their `app_users.role` allows (`current_app_role()` helper); all writes go through the service role in server code.
- 2026-10-18 — Cron route accepts both `Authorization: Bearer <CRON_SECRET>` (what Vercel Cron sends) and `x-cron-secret` (for external pingers like cron-job.org); Vercel Hobby only allows daily crons, so a 15-min schedule needs Vercel Pro or an external pinger.
- 2026-10-18 — Leasing season helper (`lib/season.ts`): leasing window Nov 1–Jul 31 per spec, but leads from Aug 1 onward count toward the *next* August's season so early fall leads aren't lost; Aug = "move-in", Sep–Oct = "pre-season". Confirm with the team.
- 2026-10-18 — AppFolio pagination follows `next_page_url` with the same POST body and `paginate_results: true`; if discovery shows the API expects GET for subsequent pages, change only `fetchReport` in `client.ts`.
- 2026-10-18 — Season definition finalized per owner: Nov 1 – Jul 31 for an Aug move-in; "current season" = the one we're in or the next one starting (Aug–Oct shows the upcoming season with zero counts until Nov 1). Supersedes the earlier "count from Aug 1" idea.
- 2026-10-18 — Seven confirmed reports (`property_directory, unit_directory, unit_vacancy, rent_roll, guest_cards, showings, rental_applications`) run sequentially with a 1.5s pause; `tenant_directory` exists but is not synced in phase 1.
- 2026-10-18 — `guest_cards` and `rental_applications` contain sensitive applicant data (income, credit score, addresses, employer, salary…): the mappers keep only an explicit allowlist and NO `raw_` jsonb copy is stored for these two reports. Note `showings` raw rows still include lead email/phone; flag if that should also be allowlisted.
- 2026-10-18 — The AppFolio database holds non-SCSH properties (51 properties / 376 units vs ~119 SCSH units), so a `properties` table carries our own `is_managed` flag: first sync marks everything managed, later-appearing properties default to unmanaged until an admin reviews them in `/admin/properties`. The Sales UI reads only through SQL views (`managed_*`, `available_units`) that join to `properties` and filter `is_managed = true`, so the filter cannot be forgotten in app code. Rows with no `property_id` are therefore excluded.
- 2026-10-18 — `units` is a composite of three reports merged in the sync (`unit_directory` base, `unit_vacancy` by `unit_id`, `rent_roll` by `unit_id` choosing one occupancy row: Current > Notice > Vacant > other > Future, latest move-in breaks ties). "Available" is defined once, in the `available_units` view: in `unit_vacancy` OR rent-roll status ≠ Current.
- 2026-10-18 — Reports that accept a date range are sent `from_date` = Aug 1 of the previous calendar year and `to_date` = today; if AppFolio rejects those params (400/422) the sync retries once without them and flags `dateParamsAccepted=false` in the result so the param names can be corrected.
- 2026-10-18 — Sales screens are URL-driven (tabs, filters, sorting are query params rendered on the server) and the whole season dataset is loaded in one request and filtered in memory — the data is small (~119 units, one season of leads) and this keeps the pages simple, bookmarkable and free of client state.
- 2026-10-18 — "Sync now" on `/admin` is a server action that calls `syncSales()` directly (same code path as the cron route) instead of HTTP-calling the route, so no secret has to be passed around; `maxDuration = 120` on that page.
- 2026-10-18 — Bug: first sign-in produced no `app_users` row because `SUPABASE_SERVICE_ROLE_KEY` held the publishable key (RLS blocked the insert) and the callback never checked supabase-js's returned `error`. Fix: `createSupabaseAdminClient` now refuses publishable/anon keys with an explicit message; provisioning moved to `lib/auth/provision.ts` which checks every error; `getCurrentUser` self-heals the row on any page load for allowed emails; failures are logged with `[auth]` prefixes and shown on the header role badge.
- 2026-10-18 — `replace_raw_rows` uses `TRUNCATE` instead of an unqualified `DELETE`: the Supabase project enforces pg-safeupdate ("DELETE requires a WHERE clause"), even inside plpgsql. Clean-table pruning already deletes with `WHERE synced_at < run` and is unaffected.
- 2026-10-18 — AppFolio Reports API silently ignores unknown request-body keys (verified with a bogus key → 200, same rows), so parameter names must be verified empirically: an invalid value on a recognised name errors or empties the result. Confirmed names: guest_cards `received_on_from/to` + `guest_card_statuses` (default = open cards only); showings `showing_date_from/to` + `statuses`; rental_applications `received_on_from/to` + `rental_application_statuses`. Status filters default to `["all"]` in `reports.ts`. Row counts 2025-08-01→today: guest_cards 77→5,023, showings 5→1,578, rental_applications 4→571.
- 2026-10-18 — Pagination per docs: `next_page_url` may be relative and must be POSTed without filters (filters are rejected on an existing report run); `client.ts` resolves it against the db origin and sends `{}`. The "dateParamsAccepted" flag was removed as meaningless; the admin page shows the exact filters sent instead.
- 2026-10-19 — Guest card grain: `guest_cards` is one row per person (`guest_card_id`). Every AppFolio row lands in `guest_card_interests` keyed by `(guest_card_id, property_id, received, row_index)`. Person `received`/`source`/`property` come from the earliest interest; `status`/`assigned_user`/`last_activity` from the most recent. `managed_guest_cards` includes a person if ANY interest is on an `is_managed` property. Property filters count a person under every managed property they inquired about; the Leads KPI still counts each person once.
- 2026-10-19 — Sign-in is company domain OR a row in `allowed_emails`. First sign-in of an allowlisted email copies that row's role onto `app_users`. Admins change roles and manage the allowlist on `/admin/users`. Domain-only users still default to viewer.
- 2026-10-19 — New `partner` role: read Sales and Accounting, not Admin. Accounting is now available; Maintenance and Customer Service stay "soon".
- 2026-10-19 — Accounting delinquency uses AppFolio `delinquency` (occupancy grain, aging buckets, last payment, NSF). `aged_receivables_detail` is pulled only for oldest unpaid invoice date → days past due. `rent_collection` / `aged_receivables` / `past_due_tenants` / `delinquency_detail` / `receivables` do not exist. No report exposes collected-this-month vs scheduled rent, so that KPI is omitted. Follow-up lives in our `delinquency_actions` table — the only user write in the app; AppFolio stays read-only.
- 2026-10-19 — Delinquency escalation ladder is admin-editable (`delinquency_stages`); current_stage = highest active stage with trigger_day ≤ days past due (invoice date, else aging-bucket lower bound). next_action_due = first due stage with no matching `delinquency_actions.stage_id`. No sending / no AI drafting in this step. Revised same day: next_action_due is the CURRENT stage only if it has no logged action — earlier unlogged stages count as skipped, so pre-existing delinquencies aren't all flagged at day 2. Overdue = current stage unlogged AND days past due > its trigger_day + 2. Admins can bulk-log the current stage ("Backfilled at go-live") for selected rows; the server recomputes stages and skips rows already logged. `tenant_directory` is synced allowlisted (occupancy_id, tenant_id, tenant, phone, email, primary) only for occupancy_ids currently on the delinquency report; partner cannot read contacts.
- 2026-10-19 — Leads and rotations live in our Supabase (`agents`, `leads`, `lead_events`, `lead_intake_rejections`, migration 0008). AppFolio tables and their sync are untouched; leads are derived from them. Identity: guest_card_id, else lowercase email, else digits-only phone (a leading US 1 is dropped). Records with neither email nor phone are logged as rejections, not created. Rotation A = arrived with form/application, B = everything else. Pick = active agent with fewest counted turns of that rotation in the last 14 days, tie → older last_assigned_at, then id. This runs in SQL (`assign_lead_by_rotation`, under an advisory lock so concurrent intakes can't double-pick). `src/lib/leads/rules.ts` mirrors it and is unit-tested with Node's built-in runner (`npm test`, no new dependency). The turn is stored on the lead (`turn_agent_id/turn_rotation/turn_at`) and stays with the original agent after an admin reassign, so reassigning doesn't rewrite rotation history. test/duplicate_of drop out of all counts and give the turn back. Leads are never deleted (trigger). Owner changes only via admin `reassign_lead` (reason required, logged). On first import, an AppFolio assigned_user matching an active agent owns the lead with no turn; afterwards the dashboard is the source of truth and `owner_mismatch` is maintained by trigger. B→A conversion keeps the owner, sets converted_from_b, consumes no A turn. B "expired" (7 days, no event) is computed at read time, not stored.
- 2026-10-22 — Lead intake (migration 0009). Go-live: the first lead import (or first PQ submission) writes `app_settings.leads_go_live_at` = now(). A lead first seen before it is never rotated: if AppFolio's assigned user is an active agent they own it (no turn), otherwise it stays unowned (no turn) for an admin to bulk-assign via `bulk_assign_leads` (no turn). Rotation only runs for leads first seen after go-live. Guest cards: `import_leads_from_appfolio()` runs at the end of every sync (only if guest_cards was written that run), in one transaction under an advisory lock shared with PQ intake. Only guest cards with ≥1 interest on an is_managed property become leads. Every guest card a person has is kept in `lead_guest_cards` (no FK, so the sync's pruning can't break identity). Each interest row = one `inquiry` event (later ones flagged `returning`); showings = `showing` events and move the stage to tour unless canceled; AppFolio's latest activity being a call/text/email moves new → contacted. Applications link to a guest card through the showing that produced them, else the same AppFolio tenant_id — applications.inquiry_id does NOT match guest_cards.inquiry_id (checked: 0 of 571), and name matching is deliberately not used; unlinked applications are logged in `lead_intake_rejections` (≈131 today). A lead whose application already exists at creation is born A (not "converted"); a B lead that later applies or submits the PQ form keeps its owner, moves to A with converted_from_b, no A turn. Application status Converted → stage leased. PQ form: POST /api/pq-submit, header X-PQ-Key = PQ_SUBMIT_KEY (compared in constant time), idempotent on submission_id via `lead_events.dedupe_key = 'pq:<id>'`; neither email nor phone → 422 and logged. `last_event_at` (7-day B expiry) now moves only on prospect activity (inquiry/form/application/showing), not on assignments or status changes. SQL was executed locally in PGlite against all migrations, a scenario fixture and a 3,600-card volume test (first import ≈1.6 s).
- 2026-10-22 — Notifications stay in n8n; the app sends no email (the planned Microsoft Graph step is dropped). Both webhooks (`/api/pq-submit`, new `/api/leads/assign`) share X-PQ-Key / PQ_SUBMIT_KEY and one response shape (SQL `lead_webhook_response`): status, lead_id, rotation, stage, lead_status, owner_agent_id, owner_name, owner_email (null when unowned), is_returning (person was already a lead), converted_from_b (lead flag), converted_now (this request moved B → A), test_mode (admin switch in `app_settings.notifications_test_mode`; n8n redirects mail when true). `/api/leads/assign` (no-form leads n8n sees): new person → B lead, owner by the normal go-live/rotation rule; known person → current owner, no turn; one inquiry event per lead + source + LA day so retries answer `duplicate`. A repeated PQ submission_id answers with the original is_returning/converted_now so an n8n retry after a timeout still emails correctly.
